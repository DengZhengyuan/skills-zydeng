# 输出格式契约

## 总规则

- 缺信息时，先输出缺口，不输出伪完整通稿。
- 信息充分时，默认先输出提纲，再输出完整稿包。
- 用户明确说 `直接出全文` 时，内部仍做提纲，但对外直接输出完整稿包。

## 缺信息输出

当会后关键事实不足时，固定按以下结构输出：

```markdown
## 待补信息
- [必需] ...
- [必需] ...
- [可选] ...

## 已确认信息
- 会议名称：
- 时间：
- 地点：
- 主办/承办：
- 已知议程或主题：
- 已知参会人：

## 成稿状态
当前不能直接生成正式会后通稿。补齐上述必需信息后再成稿。
```

要求：

- `待补信息` 按重要性排序。
- 明确区分 `必需` 和 `可选`。
- 不要在缺口未补齐时附上完整正文。

## 提纲输出

当信息充分且进入默认流程时，先按以下结构输出提纲：

```markdown
## 新闻角度
- ...

## 标题方向
1. ...
2. ...

## 段落安排
1. 导语：
2. 第二段：
3. 第三段：
4. 结尾：

## 已确认事实
- ...

## 待确认细节
- ...
```

要求：

- 提纲要短，但足以支撑用户判断结构。
- `待确认细节` 只列剩余的非阻断性问题。
- 如果已经没有待确认细节，写 `无`。

## 完整稿包输出

正式成稿时，固定按以下结构输出：

```markdown
## 标题候选
1. ...
2. ...
3. ...

## 导语
...

## 正文
...

## 发布摘要
...
```

要求：

- `标题候选` 必须给 3 个。
- `导语` 只给 1 段。
- `正文` 直接给可审改版本，不拆成过多内部说明。
- `发布摘要` 默认写成 1-2 句短摘要，适合发布时配套使用。
- 除非用户明确要求，不附加写作说明、风格解释和修改日志。

## 改稿模式输出

当任务是基于已有初稿改写时：

- 如果事实不充分，仍优先输出 `缺信息输出`。
- 如果事实充分，可直接输出 `完整稿包输出`。
- 除非用户明确要求，不额外输出“原稿问题分析”。
