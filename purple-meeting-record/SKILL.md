# purple-meeting-record

## 概述

`purple-meeting-record` 用于把嘈杂、弱结构甚至 speaker 标注不可靠的沟通转写，整理成 Purple Sys 可直接使用的记录。

它的目标不是生成一篇“像会议纪要的长文”，而是：

- 先按 `记录目标` 把 transcript 压成可筛选的原子候选项
- 再把用户确认过的关键内容沉成一套完整稿
- 最后在用户明确允许后，把 meeting note、daily 和相关 log 内容自动写回 Purple Sys
- 如果这是学生沟通场景，还要在 meeting note 与 student log 中留下稳定的“沟通形式 / 沟通建议 / 触发原因”信号，供后续学生沟通面板读取

这个 skill 默认采用四阶段交互，而不是一步到位：

1. `AI 初步清洗 + 归属判断 + 候选清单`
2. `用户修正归属并选择保留项`
3. `AI 生成完整稿包（meeting note + daily + log 追加内容）`
4. `用户明确说可以写入 -> AI 自动写入 Purple Sys`

## 核心规则

- 把 `meeting` 视为单次正式记录，先保内容，再补归属。
- transcript 是三种学生沟通形式的默认输入来源，不要求用户提供 `PPT`。
- 不把 transcript 原样改写成流水账。
- 不因为用户提供了 transcript，就默认知道全部元信息；先自行推断，再补问少量关键问题。
- `记录目标` 和 `整理档位` 是两个独立维度：前者决定主要保留什么，后者只决定保留多少 / 压缩多强。
- 不设默认 `整理档位`；若用户未明确给出档位，也没有用自然语言表达长短要求，必须先追问。
- 不把 `整理档位` 当作“总结 vs 信息记录”的替代选择；即使是 `全细节`，也需要知道是偏 `信息留存`、`结论行动` 还是 `双层记录`。
- 不把寒暄、设备调试、网络噪音、重复确认默认写入正式记录。
- 不把未经确认的关键判断强行挂到具体人名下。
- 不自动新建 student log 或 project log。
- 学生沟通场景下，只要出现明确学生对象且对应 student log 已存在，第三阶段必须生成 student log 回填草稿。
- 写入阶段默认必须写 meeting note、daily、相关既有 student log；除非用户明确说“只写 meeting note”。
- 如果不写某个相关 student log，必须说明原因：无明确个人节点、log 不存在、用户明确排除、仅参会无个人推进信息。
- 用户确认条目后，先展示一套完整稿包，而不是边确认边直接落库。
- 用户明确说“可以写入”“写入吧”“落库吧”等之后，默认把本轮已确认的 meeting note、daily 和相关既有 log 一并写入。
- 如果用户没有明确授权写入，默认停留在草稿阶段。
- “会议重要”只能提醒可能需要更高保真整理，不能替代 `整理档位` 选择。
- `后续动作 / 待跟进` 必须收紧：只写会上明确说过、被明确安排、或几乎等同于明确安排的事项。
- 不把老师追问、技术质疑、AI 推断出的合理改进自动改写成“后续动作”；这些内容应放入 `判断 / 结论`、`待澄清 / 可关注` 或正文说明。
- 如果确实需要写推测性建议，必须用谨慎措辞，例如“可考虑”“建议后续确认”“值得关注”，并标明这是从讨论推导出的建议，不得写成已经布置的任务。
- 当没有明确动作时，`后续动作 / 待跟进` 可以写“暂无明确动作”，或省略个人小节中的 `后续动作`，不要为了结构完整而编造待办。

## 组织模式

在开始整理前，先确定模式。若用户未明确说明，再根据 transcript 形态给出推荐，但不要直接替用户决定。

### 按人模式

适用于：

- 老师依次和不同学生沟通
- 多人轮流汇报近况
- 几位老师分别点评不同人的工作

按人模式的组织原则：

- 主体按人分组
- 每个人保留哪些内容由 `记录目标` 决定
- `按人 / 按事` 只决定组织方式，不隐含“只保留判断和动作”

### 按事模式

适用于：

- 围绕一个主题或少数议题展开的讨论
- 电话沟通某件事情
- 与合作方或老师就某个问题集中确认

按事模式的组织原则：

- 主体按事项分组
- 每个事项保留哪些内容由 `记录目标` 决定
- `按人 / 按事` 只决定组织方式，不隐含“只保留判断和动作”

## 学生沟通形式

当 transcript 属于学生沟通场景时，先判断它属于哪一种形式，并在正式稿包中显式写出。

固定形式只有四类：

- `月度故事汇报`
- `单独细节讨论`
- `long meeting`
- `其他`

判断原则：

- `月度故事汇报`：固定节奏、面向全组或多人参加，重点是讲完整故事，不在现场深挖细节。
- `单独细节讨论`：围绕一个或少数具体问题，适合 `30-60` 分钟局部讲透。
- `long meeting`：从 `0` 开始重建整条课题逻辑，正式讲述通常在 `1` 小时以上。
- `其他`：不属于以上三类的正式沟通。

如果无法稳定判断，先给出 AI 的初步判断，并在第一阶段元信息草稿中标为“待确认”。

## 记录目标 / 写作重心

在生成正式整理结果前，必须锁定或明确推荐 `记录目标`。它描述的是这份记录主要保留什么，不描述长短。

`记录目标` 有三类：

### 信息留存

适用于：

- 报告、讲座、访谈、对方系统讲述
- 用户更多作为倾听者，内容信息量极大
- 大部分信息是用户第一次接触，后续可能复用
- 用户明确说“这段主要是新信息”“对方讲得很多”“我是倾听者”“不要总结掉”

整理原则：

- 优先忠实保留事实、背景、行业逻辑、案例、术语、因果链和对方表达的系统框架。
- 可以降噪、去口头语、合并重复，但不能把主体压成少数结论。
- 最后可以有短的 `我的理解 / 可回看价值`，但不能替代主体信息。

### 结论行动

适用于：

- 常规推进会、决策会、学生沟通、项目协调
- 用户明确要“结论”“判断”“下一步”“落实”
- 会议价值主要在于形成决策、动作、责任人或后续判断

整理原则：

- 重点保留判断、决策、下一步、责任安排、风险和未决事项。
- 必要背景只保留到足以理解判断和动作。
- 这是旧版 skill 的主要默认写法，但现在必须显式作为 `记录目标` 处理。

### 双层记录

适用于：

- 既有大量新信息，又需要形成判断和后续动作的会议
- 学生月度汇报、技术报告会、合作方长谈等两类价值同时存在的场景
- 用户没有说清楚但 transcript 明显两者兼有时，优先推荐此目标

整理原则：

- 每个按人 / 按事小节默认拆成 `信息记录`、`判断 / 结论`；只有存在明确安排时才增加 `后续动作`。
- `信息记录` 保留事实链、方法、数据、案例、背景和对方讲述内容。
- `判断 / 结论` 只写从这些信息中形成的判断，不覆盖信息主体。
- `后续动作` 只写明确要做或需确认的事项。
- 推测性改进不进入 `后续动作`；若有记录价值，应降级为 `待澄清 / 可关注` 或写入 `判断 / 结论`。

## 整理档位 / 压缩强度

在生成正式整理结果前，必须锁定 `整理档位`。它描述的是信息保留量与压缩强度，不是会议重要性标签，也不决定记录是偏信息还是偏结论。

- 不设默认档位。
- 用户没有明确给出档位，且也没有用自然语言明确表达长短要求时，必须先问，再继续生成正式整理结果。
- 第一阶段可以先做基础清洗和候选清单，但进入第三阶段前必须锁定档位。
- 若用户只说“这是个很重要的会”，仍然信息不足，必须继续追问档位。

四级定义如下：

### 全细节

- 在当前 `记录目标` 下，尽量保留全部有效信息点、判断变化、动作安排和必要语境。
- 不主动把丰富讨论压成短纪要。
- 允许做降噪、去口头语、合并纯重复内容，但不是 transcript 逐句誊写。

### 详细

- 在当前 `记录目标` 下，保留绝大多数有效信息，允许适度归并和结构化整理。
- 可以压缩来回反复的过程性表述，但仍以完整保留为主。
- 适合“细一点，但不要脏流水账”的场景。

### 标准

- 在当前 `记录目标` 下，保留关键内容；若目标是 `信息留存`，关键内容可以是关键事实、背景、逻辑链和术语，而不只是不判断 / 动作。
- 省略大部分过程性往复和支撑细节。
- 适合常规可回看、可回填的 meeting note。

### 极简

- 只保留主题、核心信息或结论、下一步和少量必要未决事项。
- 输出应明显短于其他档位，可压到很短的摘要级别。
- 适合用户只想快速记住“这次聊了什么、定了什么、接下来做什么”。

常见自然语言可直接映射为档位：

- “不要漏任何细节”“每一句都重要”“尽量全保留” -> `全细节`
- “详细一点”“写细一点”“保留大部分讨论内容” -> `详细`
- “正常整理”“按常规 meeting note 写” -> `标准`
- “写短一点”“两三百字”“只要结论和动作” -> `极简`

如果用户没给出足够明确的表达，使用固定追问模板：

- `这次你要哪种整理档位：全细节、详细、标准、极简？`
- 如需补一行说明，可写：`全细节=尽量不漏信息；详细=保留大多数有效内容；标准=只留关键内容；极简=只留主题、核心信息或结论和下一步。`

## 元信息获取顺序

默认按以下顺序获取元信息：

1. 从文件名、路径、文本开头、已有上下文推断
2. 从 transcript 本身抽取候选信息
3. 只对仍缺失且影响结果质量的字段向用户提问

默认优先推断：

- 标题
- 日期
- 参会人候选
- 沟通模式
- 沟通形式（若属于学生沟通）
- 记录目标

`记录目标` 的处理规则：

- 用户明确说“信息”“背景”“对方讲述”“我是倾听者”“不要总结掉”等，直接采用 `信息留存`。
- 用户明确说“结论”“判断”“下一步”“落实”“动作”等，直接采用 `结论行动`。
- transcript 明显同时包含大段新信息和后续判断 / 动作，但用户未指定时，第一阶段推荐 `双层记录`，并标为“待确认或默认推荐”。
- 如果三类目标都会显著改变最终结构，且无法从输入稳定判断，先追问 `记录目标`。

`整理档位` 的处理规则：

- 不默认推断，也不因“会议重要”自动提高档位。
- 若用户已经用自然语言明确表达长短要求，直接映射到对应档位，不必重复追问。
- 若档位仍不明确，必须向用户追问。
- 未锁定档位前，不要直接进入第三阶段完整稿包。

默认只在必要时追问：

- `按人 / 按事`
- `记录目标`
- `整理档位`
- 会议标题，或用户是否接受 AI 推断标题
- 日期 / 时间
- 关键参与人或 speaker 映射

默认不阻塞输出：

- 地点 / 形式
- 完整参会人名单
- `related_projects`
- `related_people`

如果 transcript 文件名已经能稳定提供日期或标题，直接采用，并只在存在明显冲突时向用户确认。

## 第一阶段：生成工作底稿

第一阶段不要直接生成正式记录。先输出工作底稿，固定包含以下四块：

1. `元信息草稿`
2. `归属待确认`
3. `候选要点清单`
4. `建议保留项`

输出格式与写法契约见 [references/output-contract.md](references/output-contract.md)。

### 元信息草稿

写出当前可确定或可推断的关键信息：

- 整理档位
- 记录目标
- 模式
- 标题
- 日期 / 时间
- transcript 质量判断
- 参会人候选

如果某项不确定，明确标注“待确认”，不要假装确定。

若用户尚未给出 `记录目标` 或 `整理档位`，在元信息草稿中明确写出 `记录目标：待确认 / 推荐 ...`、`整理档位：待确认`，并在第一阶段结束时补问或请用户确认推荐目标。

### 归属待确认

当 speaker 标签不可靠、一个账号代表多人、或某段话无法稳定归属时：

- 先给出 AI 的初步判断
- 把不确定片段归入“未确认发言 / 多人讨论”
- 标出哪些归属会显著影响最终记录
- 等用户最终裁决

未经确认，不要把关键决定、判断或动作绑定到某个人名下。

### 候选要点清单

候选要点必须满足：

- 一条只表达一个事实、判断、动作或必要背景
- 尽量压成一句，不写长段
- 按 `记录目标` 判断记录价值，不默认只优先保留改变后续动作或判断的内容

固定标签只有五类：

- `[进展]`
- `[信息]`
- `[判断]`
- `[动作]`
- `[背景]`

编号规则固定为：

- `按人模式`：`P1.1 / P1.2 / P2.1 ...`
- `按事模式`：`T1.1 / T1.2 / T2.1 ...`

候选清单不是 transcript 摘抄。应先降噪、合并重复信息，再输出原子项。

### 建议保留项

在候选清单后，主动给出一组建议保留编号，减少用户逐条筛选的负担。

默认优先建议保留：

- `信息留存`：对方系统讲述的新信息、背景框架、术语、案例、因果链和后续可复用材料
- `结论行动`：会改变下一步动作、会改变对某人 / 某事判断、会影响长期跟踪节点的内容
- `双层记录`：同时保留信息主体和由此形成的判断 / 动作
- 所有目标下都保留少量必要语境

默认不建议保留：

- 寒暄
- 无效重复
- 设备 / 网络调试噪音
- 只帮助现场交流、但对事后记录无价值的细节

## 第二阶段：读取用户裁决

默认期望用户只回复五类内容：

- 归属修正
- 保留 / 删除的编号
- 记录目标指定
- 整理档位指定
- 少量额外要求

例如：

- “P2.1 归到张舒瑞，不是姚冬旭”
- “保留 P1.1 P1.3 P2.1，删除 P1.2”
- “这次按信息留存写”
- “每个小节分信息记录和判断动作”
- “这次按详细写”
- “把老师的总判断写得更短”
- “给张舒瑞和姚冬旭补 student log 草稿”

如果用户只给出保留编号，没有逐条说明删除项，则默认：

- 保留用户点名的编号
- 同时保留与之强依赖的少量上下文
- 删除其余低价值候选项

## 第三阶段：生成完整稿包

在用户确认条目后，不要立刻写入 Purple Sys。先确认 `记录目标` 和 `整理档位` 已锁定，再生成完整稿包，固定包含四类内容：

1. `meeting note draft`
2. `daily 今日沟通与协同` 单条草稿
3. `student log / project log` 追加草稿
4. `拟写入位置`

若 `记录目标` 或 `整理档位` 尚未锁定，先追问或请用户确认推荐值，不要直接进入第三阶段。

### Meeting Note Draft

生成 meeting note 时，遵守以下规则：

- 使用当前 Purple Sys meeting template 作为最小脚手架
- 保留 frontmatter 和 H1
- 若已知会议日期，H1 使用真实会议日期
- 只有会议日期明确时，才补 `date:` 字段
- `related_projects` 与 `related_people` 不能稳定判断时，保持空值
- `status` 默认保持 `inbox`
- 如果属于学生沟通场景，在 frontmatter 之后、总述之前增加一行稳定标记：`- 沟通形式：月度故事汇报 | 单独细节讨论 | long meeting | 其他`

正文结构由 `记录目标` 决定：

- `沟通形式`（仅学生沟通场景）
- 开头一段 `总述` 或 `信息概览`
- 主体按模式分组
- 结尾 `后续动作 / 待跟进`

`结论行动` 正文：

- 总述
- 每个关键人 / 关键事项一个小节，重点写判断、决策、动作和必要背景
- `## 后续动作 / 待跟进`

`信息留存` 正文：

- 信息概览
- 每个关键人 / 关键事项一个小节，重点写事实、背景、案例、术语、因果链和对方系统讲述
- 可选 `## 我的理解 / 可回看价值`，但篇幅应短于主体信息
- `## 后续动作 / 待跟进`

`双层记录` 正文：

- 总述
- 每个关键人 / 关键事项一个小节
- 每个小节下默认使用 `### 信息记录`、`### 判断 / 结论`
- 只有当该人 / 事项存在明确安排时，才增加 `### 后续动作`
- 对需要保留但并未明确安排的推测性建议，使用 `### 待澄清 / 可关注`，并用谨慎措辞
- 全文末尾仍可保留 `## 后续动作 / 待跟进`，但只汇总明确跨人 / 跨事项动作；没有明确动作时写“暂无明确动作”或省略该节

正文写作要求：

- 使用中文
- 先按 `记录目标` 决定写作重心，再按 `整理档位` 控制压缩强度
- 不复述对话过程
- 不保留口头语
- 不默认使用表格
- 不默认写“AI 洞察”
- `信息留存` 下不要把主体信息替换成抽象总结；`结论行动` 下只保留足以支撑判断和安排的语境
- 区分 `明确安排` 与 `谨慎建议`：前者才进入 `后续动作 / 待跟进`，后者只能放在 `待澄清 / 可关注` 或正文判断中

整理档位对正文的影响：

- `全细节`：在当前 `记录目标` 下尽量保留全部已确认的有效信息点；允许按人 / 按事归并，但不主动拔高成简短结论。
- `详细`：在当前 `记录目标` 下保留绝大多数有效信息；允许合并重复表达，压缩过程性往复，但仍以完整保留为主。
- `标准`：在当前 `记录目标` 下只保留关键内容；`信息留存` 保关键知识链，`结论行动` 保关键判断 / 决策 / 动作。
- `极简`：只保留主题、核心信息或结论、下一步和少量必要未决事项；正文应明显短于其他档位。
- 这四档主要作用于 `meeting note draft`；`daily` 与 `student log / project log` 回填草稿仍保持高密度短写，不随档位明显变长。

### Daily 回填草稿

daily 只输出一条高密度 bullet：

- 形式为“与谁沟通了什么，明确了什么”
- 若已有 meeting note 标题，优先链接 meeting note
- 不把完整会议内容塞回 daily

### Student Log / Project Log 回填草稿

只有在存在明确长期对象时才生成。

student log：

- 按人模式中，每个有实质内容的学生都要生成一条 student log 草稿；多人会议不得只写总 meeting note。
- 如果 meeting note 中有学生小节，但没有生成对应 student log 草稿，必须在 `拟写入位置` 标为“未写入”并写明原因。
- 按日期追加一个短结构，而不是自由 bullet 堆叠
- 固定字段为：
  - `来源：[[meeting note]]`
  - `本次主要汇报：...`
  - `沟通建议：继续常规月度 | 建议单独细节讨论 | 建议 long meeting | 观察`
  - `触发原因：...`
- `本次主要汇报` 要高密度总结学生这次真正讲了什么，不复制 meeting note 正文
- `沟通建议` 是给后续学生沟通面板读取的稳定信号
- `触发原因` 固定表示：为什么当前判断应继续常规月度，或为什么要升级到单独细节讨论 / long meeting
- 每条 student log 记录都必须链接回对应 `meeting note`
- 多人月度汇报时，同一篇 meeting note 可以对应多个 student log 条目；每个学生都要分别写自己的“本次主要汇报 + 沟通建议 + 触发原因”

project log：

- 只保留项目层面的决策、节点变化、依赖或明确后续动作
- 推测性项目建议若确有价值，只能用谨慎措辞写成“可关注 / 待确认”，不要写成项目已形成的待办
- 不复制 meeting note 的叙述

### 拟写入位置

在完整稿包末尾明确说明本轮准备写入哪些位置，例如：

- meeting note：`04 Record/...`
- daily：`02 Periodic/Daily/...`
- student log：`04 Record/log ...`
- project log：`04 Record/log ...`

如果某个相关 log 不存在，不要自动创建；要在这里明确标出“缺失，未写入”。如果某个 meeting note 学生小节没有对应 student log 草稿，也必须在这里标出未写入原因。

## 第四阶段：写入 Purple Sys

只有在用户明确给出写入许可后，才进入写入阶段。

可视为写入许可的典型表达包括：

- “可以写入”
- “写进去吧”
- “直接落库”
- “按这个写入 Purple Sys”

进入写入阶段前，先执行写入前检查：

1. 读取或确认相关 student log / project log 是否存在。
2. 对照 meeting note 中的学生小节，列出将写入和不写入的 student log。
3. 对每个不写入对象写明原因：无明确个人节点、log 不存在、用户明确排除、仅参会无个人推进信息。

进入写入阶段后，默认执行以下动作：

1. 创建或改写本轮 meeting note
2. 把 daily 草稿写入对应日期的 `今日沟通与协同`
3. 把相关 student log / project log 追加到对应日期条目下
4. 写入后执行回链检查：搜索 meeting note 标题，确认它已出现在 daily 和相关 student log / project log 中
5. 返回实际写入位置、未写入位置和回链验证结果

除非用户明确要求只写一部分，否则不要只写 meeting note 而漏掉 daily / log。

## Purple Sys 边界

- 这个 skill 服务 `04 Record/` 的 `meeting`，不是 `log` 的替代品。
- 这个 skill 可以给出回填草稿，但不负责决定是否新建长期 log。
- 如果用户明确说可以写入，默认把本轮已经确认的 meeting note、daily 和相关既有 log 一并写回。
- 若相关 student log / project log 不存在，只提示“可挂接对象缺失”，不要自动创建。
- 学生沟通场景下，这个 skill 负责留下稳定沟通信号；是否把这些信号进一步归并成“学生沟通面板”判断，由 [$purple-action-board](/Users/zydeng/.codex/skills/my-skills/purple-action-board/SKILL.md) 负责。

## 常见判断

### transcript 很乱时

- 先判断哪些内容是噪音
- 再判断哪些内容值得进入候选清单
- 宁可少收低价值细节，也不要把正式记录写成脏摘要

### speaker 标签明显错误时

- 先利用上下文和已知参会人做初步判断
- 明确区分“高把握判断”和“待用户裁决”
- 关键归属不明时，退回“未确认发言 / 多人讨论”

### 用户只给 transcript 和模式时

- 先自行推断标题、日期、参与人候选
- 若用户已用自然语言表达长短要求，直接映射到对应档位
- 若 `整理档位` 仍不明确，先追问档位
- 仍然先走候选清单阶段，但未锁定档位前不要直接跳正式稿

### 用户给了丰富元信息时

- 不重复追问
- 若仍缺 `整理档位`，补问这一项
- 直接进入候选清单阶段

## 执行方式

在 live vault 中工作时：

- 优先读取 transcript 文件本身，以及已有相关 daily / meeting / log 上下文
- 不为补完所有 metadata 而拖慢整理
- 用户未明确授权写入前，默认只在对话中展示完整稿包
- 用户明确授权后，自动写入 meeting note、daily 和相关既有 log
- 学生沟通写入前必须对照 meeting note 中的学生对象检查既有 student log；写入后验证 meeting note 在 daily 和相关 log 中的回链
- 写入后要说明实际落点、未写入原因和回链验证结果；若某些 log 缺失，也要说明哪些没有写成
