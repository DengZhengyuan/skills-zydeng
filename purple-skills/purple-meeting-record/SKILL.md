# purple-meeting-record

## 核心边界

- 把 meeting 作为单次正式记录，不用它替代长期 log。
- 先生成候选和完整稿包，用户明确许可后才写入 Purple Sys。
- 不自动新建 student log 或 project log。
- 不把 transcript 改写成流水账，也不把噪音写入正式记录。
- 不把未经确认的关键判断强行归到具体人名。
- `后续动作` 只记录明确安排、明确承诺或几乎等同于明确安排的事项。
- 不因结构完整而编造动作；推测性建议放入 `待澄清 / 可关注`。
- 学生沟通中，每个有实质内容且已有 student log 的学生都应获得独立回填草稿。

固定输出格式、字段和示例必须读取 [references/output-contract.md](references/output-contract.md)。

## 三个独立维度

### 组织模式

- `按人`：老师依次与不同学生/参与人沟通，或多人轮流汇报。
- `按事`：围绕一个或少数议题集中讨论。

用户未明确时，根据 transcript 推荐并标为待确认，不替用户强行决定。

### 记录目标

- `信息留存`：保留事实、背景、术语、案例、因果链和系统讲述。
- `结论行动`：保留判断、决策、责任安排、风险、未决事项和明确动作。
- `双层记录`：每个人/事项分别保留 `信息记录` 与 `判断 / 结论`；有明确安排时再增加 `后续动作`。

Transcript 同时包含大量新信息和判断/动作时，优先推荐 `双层记录`。无法稳定判断且不同选择会明显改变结构时，先确认。

### 整理档位

- `全细节`：尽量保留全部有效信息和必要语境。
- `详细`：保留绝大多数有效信息，合并重复和过程性往复。
- `标准`：只保留当前记录目标下的关键内容。
- `极简`：只保留主题、核心信息/结论、时间节点和明确下一步。

不设置隐含默认档位。“会议重要”不能替代档位。用户用自然语言明确长短时直接映射，不重复追问。

允许两层控制：

- 全局档位：整场会议的默认压缩强度。
- 局部覆盖：按人或事项单独指定，例如 `P1 详细；P2 极简`、`T1 全细节；其余标准`。

局部覆盖优先于全局档位；daily 和 log 回填始终保持高密度短写。

## 学生沟通形式

只使用：

- `月度故事汇报`
- `单独细节讨论`
- `long meeting`
- `其他`

判断不稳时给出推荐并标为待确认。用户给出的本地分类名称和修正优先，例如“个人组会，不是 long meeting”。

## 元信息

依次从文件名/路径、文本开头、transcript 和相关 vault 上下文推断：

- 标题、日期、时间
- 参与人和 speaker 映射
- 按人/按事
- 学生沟通形式
- 记录目标
- 整理档位

只追问会显著影响记录质量的缺失项。地点、完整名单和 related fields 默认不阻塞第一阶段。档位未锁定时可以生成第一阶段候选，但不能进入完整稿包。

## 四阶段流程

### 第一阶段：工作底稿

固定输出：

1. `元信息草稿`
2. `归属待确认`
3. `候选要点清单`
4. `建议保留项`

候选项必须原子化，使用 `[进展] / [信息] / [判断] / [动作] / [背景]`。按人使用 `P1.1`，按事使用 `T1.1`。先降噪和合并重复，不摘抄 transcript。

Speaker 不确定时：

- 给出高把握初判。
- 关键不确定片段退回“未确认发言 / 多人讨论”。
- 用户短消息修正的称呼、参与人和归属优先于 transcript 噪音。

### 第二阶段：用户裁决

接受紧凑回复：

- speaker/参与人修正
- 保留或删除编号
- 记录目标
- 全局档位
- 按人/事项局部档位
- 少量额外格式要求

用户只给保留编号时，保留点名内容和少量强依赖上下文，删除其余低价值项。

### 第三阶段：完整稿包

确认记录目标和档位后输出：

1. meeting note draft
2. daily `今日沟通与协同` 单条草稿
3. 既有 student/project log 追加草稿
4. 拟写入位置与未写入原因

Meeting note：

- 使用当前 Purple Sys meeting template。
- 日期明确时才写 `date`。
- related fields 无法确认时保持空值。
- 学生沟通显式写 `沟通形式`。
- 按记录目标组织正文，再按全局/局部档位控制长度。

Daily 只写一条高密度 bullet，并优先链接 meeting note。

Student log 每人按日期写：

- `来源：[[meeting note]]`
- `本次主要汇报`
- `沟通建议：继续常规月度 / 建议单独细节讨论 / 建议 long meeting / 观察`
- `触发原因`

Project log 只保留项目决策、节点、依赖和明确动作，不复制 meeting note。

### 第四阶段：写入

只有用户明确说“写入”“可以写入”“直接落库”等才执行：

1. 写入或更新 meeting note。
2. 追加 daily 草稿。
3. 追加相关既有 student/project logs。
4. 搜索 meeting note 标题，验证 daily 和每个目标 log 的回链。
5. 返回实际写入位置、未写入对象、原因和验证结果。

除非用户明确限定范围，不要只写 meeting note 而漏掉已确认的 daily/log。缺失 log 只报告，不自动创建。

## 验收

- 候选阶段与正式稿阶段分开。
- 记录目标和档位在完整稿包前已锁定。
- 局部档位覆盖得到执行。
- 信息留存没有被压成少数结论。
- 推测性建议没有进入明确动作。
- 多人学生会议没有漏掉已有 student logs。
- 未获许可时 vault 保持不变。
- 写入后 meeting note、daily 和相关 logs 的回链均已验证。
