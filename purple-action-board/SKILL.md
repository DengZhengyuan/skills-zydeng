# purple-action-board

## 概述

`purple-action-board` 是 Purple Sys 之上的“行动判断层”。

它不创建正式 task 库，不要求用户手工维护待办，也不替代 `purple-periodic`。它的职责是：

- 从 Purple Sys 的事实层提炼行动线程
- 维护未来 7 天承诺与待闭合小事
- 回捞曾被记录、后来沉下去、但可能仍值得重新判断的事项
- 在用户需要时判断“现在更该做什么”
- 区分“推进中”“等待条件”“待确认完成”“可忽略”
- 把结果写入固定页面 `00 Dashboard/AI 行动面板.md`
- 把学生沟通判断写入固定页面 `00 Dashboard/学生沟通面板.md`
- 吸收 `AI 行动面板` 每个项目/线程字段区里的 `人工修正 / 交互输入`

当用户想知道“下一步该做什么”“哪些事情卡住了”“最近哪些重要事项没推进”“更新行动面板”时，应使用本 skill。

## 核心规则

- 这是按需分析系统，不是主动提醒系统。
- 只基于 Purple Sys 自身记录做判断，不创建正式任务库，不要求用户手工维护一套 task。
- 不把 daily 中每个 bullet 直接变成线程；面板以“眼前动作 + AI 项目判断 + 辅助防遗忘区”组织，而不是按单条记录组织。
- 默认不扫描整个 vault，必须控制来源范围。
- 重要但暂时推进不了的事项，放入 `等待条件`，不要误判为普通拖延。
- 允许从旧记录中回捞“曾被记录、后来没有继续推进、但可能仍有价值”的事项，但必须先做筛选和归并，不能把零碎记录直接堆成待办。
- Purple Sys 默认全部视为工作相关内容，不再额外区分“工作 / 非工作”。
- 不再维护一个泛泛的“零碎不能归类事项池”；短期动作默认来自 recent daily 里的 `未来几天需要做的事情` 和 `今日杂项 / 触发事项`。
- 默认启用“候选审阅模式”：先整理候选、再由用户确认、最后才重写面板。
- 默认采用逐条确认、三档推荐、宁多勿漏的取向。
- 对旧条目，`没有新证据` 不能直接等于 `可以放掉`；仍重要的事项应先候选转入 `等待条件`。
- 用户的判断应写回行动面板本身，而不是只停留在对话中。
- `AI 行动面板` 与 `学生沟通面板` 分工固定：前者负责全局主线程，后者负责全体 `ongoing` 学生的月度覆盖与沟通分流。
- 学生相关线程默认进入 `学生沟通面板`；只有直接牵动近期主攻或明确占用用户行动资源的学生线，才进入 `AI 行动面板`。
- `AI 行动面板` 的每个 `### 项目/线程` 字段区允许存在 `人工修正 / 交互输入`；下次重算时必须优先读取这些纠偏输入。

## 触发范围

以下场景触发：

- “我接下来该做什么”
- “更新行动面板”
- “最近哪些重要事情没推进”
- “帮我判断哪些线程更紧急”
- “基于 Purple Sys 给我下一步建议”
- “有哪些重要但暂停的事别忘了”
- “帮我盯一下未来几天要做的事情”
- “吸收一下面板里的人工修正”
- “哪些学生该单独讨论”
- “哪些学生该做 long meeting”
- “谁欠了一次月度汇报”
- “更新学生沟通面板”

以下场景不触发：

- 普通 daily 总结
- weekly / monthly 常规汇总
- 单纯归档 daily 到 log

普通 periodic 工作流仍由 [$purple-periodic](/Users/zydeng/.codex/skills/my-skills/purple-periodic/SKILL.md) 处理。

## 默认输出

- 候选审阅阶段：先在对话中输出候选审阅清单，格式遵循 `references/review-contract.md`
- 固定页面：`00 Dashboard/AI 行动面板.md`
- 学生沟通页面：`00 Dashboard/学生沟通面板.md`
- 默认更新方式：用户确认后整体重算覆盖
- 旧面板只作为参考读取，不做局部拼补

正式行动面板的固定结构与字段契约见 `references/board-contract.md`。候选审阅阶段的输出契约见 `references/review-contract.md`。

学生沟通面板的正式页面契约见 `references/student-board-contract.md`。学生沟通候选审阅契约见 `references/student-review-contract.md`。

## 信息读取规则

默认按四层读取，而不是只看增量：

1. `变化层`
   - 上次行动面板更新之后新增的 `record / material / project log / student log`
   - 用同时间段的 daily / weekly 补上下文
2. `短期背景层`
   - 最近 14 天的 periodic notes
   - 与其明确相关的 project / student / admin logs
3. `中期背景层`
   - 最近 1 个月的 weekly notes
   - 关键 logs
4. `长周期回溯层`
   - 默认不读
   - 用户明确要求时，扩展到最近 3 个月

优先级：

- 旧条目是否被推进：优先看 recent `record / material / project log / student log`
- daily：原始推进、当天事实和短期承诺的补充层
- weekly：阶段性判断、阻塞和重点方向
- material / meeting：只在反复出现或提供关键决策时读取

如果本次任务更新 `AI 行动面板`，还要额外读取：

- recent daily 中的 `未来几天需要做的事情`
- recent daily 中的 `今日杂项 / 触发事项`
- 旧面板每个项目/线程里的 `人工修正 / 交互输入`

如果学生沟通面板在本次任务范围内，额外读取优先级为：

- 所有 `record_type=log-student` 且 `status=ongoing` 的学生 log
- 最近学生相关 meeting note 中的 `沟通形式`
- student log 条目中的 `本次主要汇报 / 沟通建议 / 触发原因`
- 最近 4-8 周内可作为月度覆盖证据的 `月度故事汇报 / long meeting`

除“当前线程”外，也允许从较早记录中识别“沉底事项”：

- 事项曾在 daily、weekly、project/log、meeting、material 中被明确记录
- 近期没有新的推进证据
- 但从内容判断，仍可能对后续工作有帮助，或值得用户重新决定去留
- 这类事项默认不直接进入面板，而是先作为“回捞候选”进入判断流程

## 旧条目处置规则

每次更新已有行动面板时，都要先对旧条目做候选分流，而不是直接重写页面。

旧条目候选固定分成 4 类：

- `建议更新保留`
- `建议转等待条件`
- `建议放掉`
- `证据不足，需你判断`

判定原则：

- 只要看到上次面板之后有明确推进证据，优先列入 `建议更新保留`
- 没看到推进证据，但从上下文看仍重要，默认列入 `建议转等待条件`
- 只有在近期证据明显表明 `已完成 / 已失效 / 已被别的线程覆盖` 时，才列入 `建议放掉`
- 如果证据冲突、过旧、或不足以稳定判断，放入 `证据不足，需你判断`
- `没有新证据` 本身不能直接等于 `可以放掉`

## 线程提取规则

面板按“线程”组织，而不是按单条 bullet 组织。

线程示例：

- `Paper 3 收尾`
- `二维床 / CFB 合同与采购`
- `泰格开题准备`
- `刘博异常压降排查`
- `年度预算`
- `某学生当前方向收束`

提取规则：

- 有现成 project/log 时，优先归到对应线程。
- 没有 project/log，但近期反复出现且有明确下一步时，也允许进入候选。
- 只出现一次、没有后续动作的碎片，不进入候选。
- 不要因为一次短期主题，就自动新建 project 或 log。

## 眼前动作规则

`AI 行动面板` 不再维护泛化的小事项池，而是把具体动作置顶为固定区块：`眼前动作`。

这个区块固定分成三类：

- `未来7天承诺`
  - 来自 recent daily 的 `未来几天需要做的事情`
  - 代表未来 `7` 天内用户明确强调的短期承诺
- `待闭合小事`
  - 来自 recent daily 的 `今日杂项 / 触发事项`，或候选审阅中被用户明确要求保留的小尾巴
  - 代表已经发生、但短期内仍需闭合的 follow-up
- `已完成待移出`
  - 代表已经完成、失效或即将清理出面板，但本轮仍需要给用户看到的动作
  - 下次更新时应优先确认是否移出正式面板

与项目线程的分界：

- 项目线程：有稳定主题、会持续跟进、或会牵动多个动作 / 依赖
- 眼前动作：更像即时动作、短 follow-up、临时节点或未来 `7` 天承诺

状态迁移：

- 如果某眼前动作后续反复出现、形成依赖链、或明显牵动主线，应升级为正式线程
- 如果某眼前动作转为外部依赖，应移入 `等待条件`
- 如果某眼前动作已完成或明显失效，应先进入 `已完成待移出` 或直接移出面板

如果某条眼前动作本来已经属于一个主线程：

- `眼前动作` 优先展示即时动作
- 主线程只保留长期背景，不重复展开同一动作

## 新条目候选提名规则

新条目生成时，不直接给最终面板，而是先给候选池。

候选固定分成两类：

- `新线程候选`
- `新短期事项候选`

并按三档推荐等级分层：

- `强推荐`
- `推荐`
- `候补观察`

默认取向是宁多勿漏，但必须靠推荐等级和证据做收束。

推荐等级含义：

- `强推荐`：最近证据强、下一步明确、现在就值得占用注意力
- `推荐`：有动作意义，但优先级略低或仍需用户裁决
- `候补观察`：有价值但证据或时机还不够，优先供用户做“不漏项”检查

提名原则：

- 优先提名 recent 反复出现、带明确下一步、能牵动主线的主题
- 同一主题如果尚不足以成为主线，但确有动作意义，先作为短期事项候选而不是直接丢弃
- 沉底事项回捞时，也先进入候选池，不直接落板

## 沉底事项回捞规则

除了当前活跃线程外，还要识别“曾被记录、后来沉下去”的候选事项。

回捞条件：

- 该事项在 Purple Sys 中出现过，且内容可识别，不是完全无法命名的碎片
- 虽然近期没有新证据，但仍可能对后续研究、实验、论文、行政或系统建设有帮助
- AI 无法仅凭现有记录判断它应继续推进、等待条件、已完成还是可忽略

回捞原则：

- 不要求它曾经是高优先级主线；只要“被记录过且可能仍有价值”即可进入候选
- 不把单条 bullet 原样搬上面板；需要先判断它应进入线程候选还是小事项候选
- 明显已经失效、已被后续内容覆盖、或只是随手记录且无后续意义的内容，不必回捞
- 第一次系统梳理时，可以集中回捞一轮；后续更新只挑少量最值得恢复判断的事项

## 候选审阅与确认机制

每次更新已有行动面板前，默认执行两阶段流程：

1. 读取旧面板
2. 读取新增事实和近期背景
3. 先输出旧条目处置候选
4. 再输出新条目候选
5. 等用户逐条确认
6. 根据用户确认结果，整体重算新版面板

首次生成面板时，也使用同样流程，只是不输出“旧条目处置候选”，只输出“新条目候选”。

默认的旧条目可确认动作：

- 更新保留
- 转等待条件
- 放掉
- 暂不动

默认的新条目可确认动作：

- 放入眼前动作
- 放入近期重点
- 放入近期变化待判断
- 放入等待条件
- 待确认完成
- 可忽略
- 放掉
- 本次不放入

如果候选很多，可以按类别展示，但默认仍应支持逐条确认。

## 人工修正 / 交互输入规则

`AI 行动面板` 的每个 `### 项目/线程` 字段区，都允许存在一行固定字段：`- 人工修正 / 交互输入：`。

该输入只作用于当前项目/线程，不作为整个 section 的纠偏输入。`眼前动作` 内的短期 bullet 不单独挂输入字段；如果某条短期事项反复需要纠偏，应优先考虑升级成正式 `### 项目/线程`。

它的用途不是长期批注，而是当 AI 判断和用户想法不一致时，给下一次重算提供纠偏输入。

推荐形状：

```md
- 人工修正 / 交互输入：
```

读取规则：

- 更新面板时，先读旧面板每个项目/线程里的 `人工修正 / 交互输入`
- 当前标准格式是一行字段：`- 人工修正 / 交互输入：`
- 兼容读取旧格式小块：`#### 人工修正 / 交互输入` 及其下方注释内容；生成新版面板时不再输出旧格式小块
- 该输入只作用于其紧跟的项目/线程，不能串到同一 section 的其他项目
- 再读新增证据和短期承诺层
- 已被吸收的输入默认从输入字段清掉
- 不新增单独归档页
- 只有带 `#留摘要` 的输入，吸收后才把处理结果压成一句写进 `本次更新时向用户确认的判断`
- 项目类修正默认不要求标记；吸收后直接清掉
- 有未处理交互输入的项目，重算时不要随意改 `###` 标题
- 若必须改标题、合并线程或移走项目，必须把旧输入的意图带到新判断里，再清掉旧输入

## 学生沟通面板规则

学生沟通面板是 `purple-action-board` 的第二输出面，而不是独立 skill。

它的目标是：

- 判断所有 `ongoing` 学生是否欠一次月度正式覆盖
- 判断哪些学生更适合 `单独细节讨论`
- 判断哪些学生已经到了应做 `long meeting` 的阶段
- 提醒哪些学生看起来可能不再适合继续标为 `ongoing`
- 给下一轮沟通生成简短会前包

### active 学生默认来源

默认把所有满足以下条件的对象视为 active 学生：

- `record_type = log-student`
- `status = ongoing`

系统不能直接把某位学生移出 active；只能在候选审阅阶段提出：

- `可能不再 ongoing`
- `建议转 paused`
- `建议转 closed`

### 月度覆盖规则

月度覆盖只看两类有效事件：

- `月度故事汇报`
- `long meeting`

`单独细节讨论` 不抵扣月度覆盖。

如果某位 `ongoing` 学生距离最近一次有效覆盖已超过 `28` 天，应进入 `月度欠账候选`。

### 沟通形式分流规则

`建议单独细节讨论`：

- 问题边界相对清楚
- 更像局部方法、定义、图表、数据、实验或推进卡点
- 预计 `30-60` 分钟能讲透

`建议 long meeting`：

- 问题已经上升为整条课题逻辑重建
- 学生需要从 `0` 开始把背景、问题、方法、证据链和路线完整讲顺
- 或已经进入开题、论文收束、阶段收口等关键节点

`可能不再 ongoing`：

- 近期长期无推进
- 角色或培养状态变化明显
- 或记录显示其已明显退出当前持续指导节奏
- 但证据还不足以直接改 frontmatter 状态

### 学生沟通候选审阅

学生沟通候选固定分成四类：

- `月度欠账候选`
- `建议单独细节讨论候选`
- `建议 long meeting 候选`
- `可能不再 ongoing 候选`

用户可确认动作固定为：

- `保持常规月度`
- `建议单独细节讨论`
- `建议 long meeting`
- `继续视为 ongoing`
- `建议转 paused`
- `建议转 closed`
- `本次不放入`

### 学生沟通附加辅助能力

当本次任务范围包含学生沟通判断时，固定额外产出三类帮助：

- 找出谁已经欠一次月度正式覆盖
- 为下一轮月度故事汇报给出建议名单
- 为进入 `建议单独细节讨论` 或 `建议 long meeting` 的学生生成简短会前包：
  - 这次要讲清的核心问题
  - 下次必须带来的图 / 数据 / 材料
  - 预期要形成的结论

## 行动面板状态使用原则

固定状态只有 4 类：

- `推进中`
- `等待条件`
- `待确认完成`
- `可忽略`

判断原则：

- `推进中`：近期仍在推进，或现在值得继续推进
- `等待条件`：重要，但当前受外部依赖、时机、资源或主观判断限制，短期无法推进
- `待确认完成`：从记录看大概率已完成，但信息不足以完全确认
- `可忽略`：不再重要、已失效或暂时不值得占用注意力

额外原则：

- 旧条目近期没有新证据，但仍明显重要时，应优先候选转入 `等待条件`
- `候补观察` 只是候选审阅阶段的推荐等级，不进入正式面板

如果用户明确说“这件事最近做不了，但别忘了”，应放入 `等待条件`，以后每次更新仍继续显示。

## 用户判断的落点

用户对线程与学生沟通候选的判断，默认写回对应面板本身，而不是分散写回原始 logs。

写回规则：

- 最终面板只写入用户确认保留或纳入的内容
- 用户确认 `本次不放入` 的新候选，不进入主板，但要写进 `本次更新时向用户确认的判断`
- 用户确认 `放掉` 的旧条目，不再进入主板，但要写进 `本次更新时向用户确认的判断`
- 用户确认从旧区块迁移到 `等待条件` 的条目，也要写进 `本次更新时向用户确认的判断`
- 默认不新增常驻 `候补观察` 区块，避免面板长期膨胀
- 学生沟通候选的确认结果写入 `学生沟通面板` 的 `本次更新时确认的判断`
- 已吸收的 `人工修正 / 交互输入` 默认从输入字段清掉；只有带 `#留摘要` 的输入才在摘要区留一句处理结果

## 执行方式

当用户在 live vault 中工作时，优先使用 `obsidian-cli` 读取内容。

典型流程：

1. 先读取现有行动面板；如果不存在，则按首次生成处理。
2. 先读取旧面板每个项目/线程里的 `人工修正 / 交互输入`。
3. 按四层规则读取所需来源，并优先判断上次面板后的 `record / material / log` 变化，以及 recent daily 里的短期承诺层。
4. 按 `references/review-contract.md` 产出候选审阅清单，不直接写面板。
5. 等用户逐条确认。
6. 按 `references/board-contract.md` 的固定结构整体重写 `00 Dashboard/AI 行动面板.md`，在每个保留的项目/线程字段区保留空输入字段，保留未吸收的人工输入，清掉已吸收输入。

如果本次任务涉及学生沟通判断，追加以下流程：

7. 读取现有 `00 Dashboard/学生沟通面板.md`；若不存在，则按首次生成处理。
8. 基于 `ongoing log-student`、最近 student log 条目与相关 meeting note，按 `references/student-review-contract.md` 产出学生沟通候选审阅。
9. 等用户确认学生候选。
10. 按 `references/student-board-contract.md` 的固定结构整体重写 `00 Dashboard/学生沟通面板.md`。

## 测试与验收

更新或使用本 skill 时，至少应能稳定识别出以下类型的线程：

- `Paper 3`
- `二维床 / CFB`
- `泰格开题`
- `刘博异常压降`
- `预算`

并将其放入合理区块，而不是简单复述 recent daily。

同时应满足：

- 旧条目在上次面板后有明确 `log / record / material` 推进证据时，应进入 `建议更新保留`
- 旧条目近期无推进，但仍明显重要时，应进入 `建议转等待条件`，而不是直接掉出面板
- 旧条目近期有完成或失效证据时，应进入 `建议放掉`
- 新出现的强信号主题，应进入 `新线程候选 / 强推荐`
- 单步可执行但不构成长期主线的事项，应进入 `新短期事项候选`
- 用户确认 `本次不放入` 的新候选，不进主板，但会在摘要中留下本次判断
- 用户确认 `放掉` 的旧条目，不再出现在主板，但会在摘要中留下放掉记录
- 候选列表可以偏长，但最终主板仍应明显比候选清单更收敛，不退化成待办清单
- recent daily 里的 `未来几天需要做的事情` 应进入 `眼前动作 / 未来7天承诺`，而不是被误判为已发生事实
- 项目/线程里的 `人工修正 / 交互输入` 应在下次更新前被优先读取，并在吸收后默认清掉
- 带 `#留摘要` 的人工修正吸收后，应在 `本次更新时向用户确认的判断` 留下一句处理结果
- 学生沟通面板能够稳定识别 `月度故事汇报 / 单独细节讨论 / long meeting`
- `单独细节讨论` 不会被误算为月度覆盖
- 超过 `28` 天未出现 `月度故事汇报 / long meeting` 的 `ongoing` 学生，应进入 `月度欠账候选`
- 对长期无新证据的 `ongoing` 学生，应优先进入 `可能不再 ongoing 候选`，而不是直接从台账消失
