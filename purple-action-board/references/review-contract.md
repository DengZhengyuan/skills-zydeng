# 行动面板候选审阅契约

该契约用于“候选审阅阶段”的对话输出，而不是最终落入 `00 Dashboard/AI 行动面板.md` 的正式页面。

默认目标：

- 先让 AI 做初步整理和判断
- 再让用户逐条确认
- 最后才按 `board-contract.md` 重写正式面板

## 固定结构

候选审阅阶段默认按以下顺序输出：

1. 标题
2. 一段简短说明
3. `旧条目处置候选`
4. `新线程候选`
5. `新短期事项候选`
6. `建议你逐条确认的动作`

首次生成面板时，没有旧面板可参考，可以省略 `旧条目处置候选`。

## 候选编号规则

候选审阅中的每个可操作 item 必须带全局连续编号，方便用户直接按编号确认动作。

- 编号从 `旧条目处置候选` 的第一条开始
- 编号跨 `旧条目处置候选 / 新线程候选 / 新短期事项候选` 连续递增
- 分组标题仍保留，但不能在新分组中重新从 `1` 开始
- 编号只用于候选审阅阶段，不进入正式 `AI 行动面板`
- `建议你逐条确认的动作` 中必须按同一编号引用候选

## 标题与说明

标题建议固定为：

```markdown
# 行动面板候选审阅
```

说明区需要简要写清：

- 本次读取的时间范围
- 这是候选审阅，不是最终面板
- 默认采用逐条确认
- 候选取向是宁多勿漏
- 如果本次还涉及学生沟通判断，应明确说明学生候选改走 `student-review-contract.md`
- 如果旧面板存在项目/线程里的 `人工修正 / 交互输入`，应明确说明本次会优先吸收这些纠偏输入

## 旧条目处置候选

旧条目处置候选固定分成 4 类：

- `建议更新保留`
- `建议转等待条件`
- `建议放掉`
- `证据不足，需你判断`

每条旧条目候选至少应包含以下字段：

- `编号`
- `条目名`
- `当前所在区块`
- `最近新增证据`
- `AI 建议动作`
- `建议理由`

建议格式：

```markdown
### 1. 条目名

- 当前所在区块：AI 判断：近期重点项目
- 最近新增证据：2026-04-02 组会；log 某学生
- AI 建议动作：建议转等待条件
- 建议理由：最近没有实质推进，但主题仍重要，不能直接放掉
```

## 新条目候选

新条目候选固定分成两类：

- `新线程候选`
- `新短期事项候选`

每一类都按三档推荐等级分层：

- `强推荐`
- `推荐`
- `候补观察`

每条新条目候选至少应包含以下字段：

- `编号`
- `候选名`
- `建议放入位置`
- `推荐等级`
- `最近证据`
- `建议下一步`：只在证据明确时写具体动作；推测性内容必须写成“可考虑 / 待确认 / 保持观察”
- `为什么这次值得讨论`

建议格式：

```markdown
### 8. 候选名

- 建议放入位置：AI 判断：近期重点项目
- 推荐等级：强推荐
- 最近证据：2026-04-01 daily；2026-04-02 组会
- 建议下一步：先把问题边界拉清，再安排一轮推进
- 为什么这次值得讨论：最近反复出现，且已经开始牵动主线
```

`建议下一步` 的收紧规则：

- 只有明确承诺、明确未闭合事项、真实阻塞或高置信度延续线程，才写成具体行动。
- 普通讨论、老师追问、会议 critique 或 AI 推断出的合理改进，不写成行动项；如需保留，写成“可考虑后续确认”“待用户判断是否纳入”。
- 对证据不足的新候选，优先给 `候补观察`，不要为了不漏项而扩写成待办。

## 用户可确认的动作

默认的旧条目可确认动作：

- 更新保留
- 转等待条件
- 放掉
- 暂不动

默认的新条目可确认动作：

- 放入眼前动作
- 放入近期重点
- 放入近期变化待判断
- 放入等待条件
- 待确认完成
- 可忽略
- 放掉
- 本次不放入

如果候选较多，可以按类别展示，但必须保留逐条确认的能力。

用户确认时应优先支持按编号批量表达，例如：

```markdown
1 更新保留
2 转等待条件
3 放掉
8 放入眼前动作
9 放入近期重点
10 放入近期变化待判断
```

## 输出边界

- 候选审阅阶段不要直接重写正式面板
- 候选编号不能进入正式 `AI 行动面板`
- 候选可以偏长，但必须用推荐等级和证据做收束
- `候补观察` 只存在于候选审阅阶段，不进入正式面板
- 对旧条目，`没有新证据` 不能直接等于 `建议放掉`
- 不要在这里输出全员学生沟通台账；学生沟通审阅另走 `student-review-contract.md`
- 学生相关候选默认转由 `学生沟通面板` 承接；只有直接牵动近期主攻或明确占用用户行动资源时，才建议进入 `AI 行动面板`
- 如果旧面板里某个项目/线程的 `人工修正 / 交互输入` 已被新证据吸收，应在相关候选理由里体现其已被处理，而不是把原批注原样搬进正式候选
- 项目/线程里的交互输入只作用于对应项目；同一 section 下其他项目不能继承这条纠偏
- 有未处理交互输入的项目，候选阶段不要随意改名；若必须改名、合并或移走，应在候选理由中说明旧输入如何被吸收
